# SQLiteSyntax

Swift types for SQLite's SQL syntax, generated from SQLite's own language definition, plus a parser
that turns SQL text back into those types.

```swift
import SQLiteSyntax
import SQLiteParser

let statement = try SQLStatement(parsing: "SELECT a, b FROM t WHERE a > 1 ORDER BY b DESC")
print(try statement.sql())          // SELECT a , b FROM t WHERE a > 1 ORDER BY b DESC

let expression = try Expression(parsing: "price * (1 + tax)")
```

## Targets

| Target | What it is |
|---|---|
| `SQLiteSyntax` | The syntax types. `Generated/` is produced by the generator; `Core/` (expressions, literals, names, the builder) and `Convenience/` (builder API, literals) are hand-written. |
| `SQLiteParser` | Tokenizer, expression parser (precedence climbing) and generated `parse(_:)` functions. Every top-level type gets `init(parsing:)`. |
| `GrammarExtraction` | Reads the railroad diagrams in the SQLite docs (pikchr → SVG → graph → EBNF) and checks each extracted rule against its diagram. macOS only (uses `XMLDocument`). |
| `SyntaxGeneration` | Turns the EBNF plus `Grammar/codegen.json` into Swift types and parsers, and reads precedence/keyword tables from SQLite's sources. |
| `sqlite-grammar` | Command-line tool that runs both of the above. |
| `GenerateGrammar` | Package plugin that runs `sqlite-grammar` with this package's paths. |

## Regenerating

The generator needs two sibling checkouts next to this package:

```
SQLite/
  SQLiteSyntax/          this package
  sqlite-docsrc-git/     https://sqlite.org/docsrc (syntax diagrams)
  sqlite/                https://sqlite.org/src (parse.y, mkkeywordhash.c, test suite)
```

Then:

```bash
swift package --allow-writing-to-package-directory generate-grammar
```

This rewrites:

- `Grammar/sqlite.ebnf`: the grammar extracted from the diagrams.
- `Sources/SQLiteSyntax/Generated/*.swift`: the syntax types, one per rule.
- `Sources/SQLiteSyntax/Generated/SQLiteTables.swift`: operator precedence (from `parse.y`) and keyword classes (from `mkkeywordhash.c` and parse.y's `%fallback ID`), for a default build. This is only regenerated when the `sqlite` checkout exists; pass `--sqlite-source <path>` to use another location.
- `Sources/SQLiteParser/Generated/*+Parsing.swift`: the parse functions.

Generated files start with a `// Generated by sqlite-grammar` header. Files with that header are deleted
and rewritten on every run. Never edit them by hand: change the generator or `codegen.json` instead.

Pass `--docs <path>` to the plugin for a docs checkout somewhere else. `--verbose` reports per-diagram
diagnostics. The tool can also be run directly: `swift run sqlite-grammar --help`.

After regenerating, run the tests:

```bash
swift test
```

To check agreement with SQLite on its own test suite (about 48,000 statements; see `Grammar/CORPUS.md`):

```bash
SQLITE_CORPUS=1 swift test -c release --filter CorpusTests
```

## `Grammar/codegen.json`

This file controls which rules become Swift types and how they look.

| Key | Meaning |
|---|---|
| `rules` | Grammar rules to generate types for. A rule that isn't listed stays inline wherever it is used. |
| `references` | Rules implemented by hand in `Core/`, e.g. `"expr": "Expression"`. Generated code refers to the Swift type; nothing is generated for the rule. |
| `tokens` | Rules that map to an existing Swift type instead of their own, e.g. `"table-name": "Name<Table>"`. |
| `keywordEnums` | Keyword alternatives that become a shared enum, e.g. `"ASC|DESC": "SortDirection"`. |
| `names` | Overrides for generated type, case and property names, keyed by the rule or fragment they come from. |
| `extraRules` | Helper rules added to the grammar before generation (e.g. `limit-clause`), so a repeated fragment becomes one named type. A fragment whose language equals a rule's is replaced by a reference to that rule. |
| `grammarPatches` | Find/replace edits on a rule's EBNF, for syntax that parse.y accepts but the diagrams omit. Each patch says why it exists. |
| `namespace`, `public` | Whether generated types are nested in a namespace (`""` for top-level), and whether they are `public`. |

The generator handles recursion itself. Recursive enums become `indirect enum`, and cycles made only
of structs get an `@Indirect` box. A `{ ',' x }` list becomes a `[X]` array, with a non-empty check
in `validate()` where the grammar requires at least one item.

## Migrating a rule

To move a rule from hand-written code (or from inline) to a generated type:

1. Add the rule name to `rules` in `codegen.json`. If it was in `references` or `tokens`, remove it from there.
2. Regenerate, then read the new file in `Sources/SQLiteSyntax/Generated/`. The doc comment on each type and case shows the EBNF it came from.
3. Fix any awkward names with `names` overrides. If the same fragment shows up in several types, add an `extraRules` entry so it becomes one shared type.
4. Delete the hand-written type. Update `Convenience/` if it built that type, so the public API stays the same.
5. If the hand-written parser in `SQLiteParser` (the expression parser and hand-written conformances in `ParserRuntime.swift`) parsed the old type, switch it to the generated `parse(_:)`.
6. Run `swift test` and the corpus test. A new disagreement with SQLite usually means the diagram differs from parse.y. Add a `grammarPatches` entry if the syntax matters in practice, or record it in `Grammar/CORPUS.md`.

## Platform notes

- The generator (`GrammarExtraction`, `SyntaxGeneration`, `sqlite-grammar`) runs on macOS only.
- `SQLiteSyntax` and `SQLiteParser` embed their keyword and precedence tables, so they don't depend on the SQLite library at runtime.
- The tests link the system SQLite to compare against it.
